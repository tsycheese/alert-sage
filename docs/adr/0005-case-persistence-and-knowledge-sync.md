# ADR 0005：案例事实与知识库同步解耦

## 状态

已接受，V1.4 实施。

## 背景

人工批准后既要立刻形成可审计案例，又要把案例发布到 Dify 等外部知识库。把发布直接放进 LangGraph `finalize` 会让节点恢复时重复产生外部副作用，并让供应商故障阻塞已完成的人工决策；只保留外部文档又会丢失本地业务事实和重试依据。

## 决策

- 批准终态、结构化 `cases` 记录和 `case_created` 事件在同一 PostgreSQL 事务内提交。
- 事务提交后投递独立 `alert_sage.case.sync` Celery 任务。
- 同步任务只依赖 `CasePublisher` 协议，以 `case-sync:{case_id}` 作为稳定幂等键；V1.4 使用 `MockCasePublisher`，后续增加 Dify 实现。
- PostgreSQL 保存同步状态、尝试次数、外部文档 ID、错误和审计事件；Redis 只提供队列、短期锁和事件唤醒。
- 工作流完成与知识同步成功是两个状态：外部同步失败不回滚人工批准，允许通过 API 独立重试。

## 备选方案

### 在 `finalize` 节点直接调用 Dify

实现较少，但外部延迟会占用工作流任务，恢复重入容易重复发布，供应商错误还会污染核心工作流终态，因此不采用。

### 事务性 Outbox

能够消除数据库提交与 Celery 投递之间的崩溃窗口，可靠性最好，但需要额外消息表、投递器和清理策略。V1.4 保留显式状态与人工重试，Outbox 按路线图在 V2 引入。

## 影响

- Dify 可替换且不参与核心告警编排。
- 页面能区分案例已生成、正在同步、同步成功和失败。
- 当前仍存在事务提交后、任务投递前进程退出的短窗口；在 Outbox 落地前需要通过失败可见性与人工重试补偿。
