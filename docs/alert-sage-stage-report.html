03 / FEISHU LOOP

告警群里完成诊断与人工确认

群卡片展示共享状态，私聊卡片提醒审批人。所有按钮都重新进入后端校验，不能绕过业务状态机。

告警接入

warning / critical 且来源命中白名单时生成共享卡片意图。

群内通知

Bot 发送单一公共卡片，包含严重级别、状态与 Web 链接。

手动启动

群成员点击启动；行锁与活动运行唯一索引吸收竞争。

异步诊断

queued → running，真实 DeepSeek + Dify 在 Worker 中运行。

等待确认

共享卡片更新，审批白名单同时收到幂等私聊提醒。

最终收敛

批准、驳回或重新分析；群卡片和私聊提醒进入终态。

Human-in-the-loop
不是一个按钮，而是一条可靠事务。

回调事实、业务命令与 Outbox 意图在同一个 PostgreSQL 事务中提交。

批准完成工作流，创建结构化案例并异步同步 Dify。
驳回进入 rejected 终态，不伪造案例或知识同步结果。
重新分析反馈必填、最长 1,000 字，每个运行最多三次。
04 / RELIABILITY

外部系统失败时，系统不编造成功

R01 · IDEMPOTENCY

重复投递只产生一个业务事实

event ID、正文哈希、报告决策约束、告警行锁与活动运行唯一索引共同吸收重复事件、重复按钮和 Web/飞书竞争。

R02 · OUTBOX

状态事实与投递意图一起提交

飞书失败不会回滚告警事实；Redis 或 Broker 暂时不可用时 Outbox 保持 pending，恢复后继续投递。

R03 · REVISION

旧卡片任务不能覆盖新状态

Worker 从 PostgreSQL 读取最新状态渲染；desired / delivered revision 控制乱序，旧 nonce 点击会被拒绝。

R04 · VENDOR FAILURE

供应商故障保持可见

DeepSeek 不可恢复失败进入 failed；Dify 检索失败标记知识缺失，案例同步保持独立状态并可重试。

05 / ACCEPTANCE

真实调用通过，离线回归也保持稳定

人工 live 证据与自动化契约覆盖分开记录，避免把只在测试里通过的边界误报为人工验收。
